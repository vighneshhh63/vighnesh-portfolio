Evil Mannequins
Summary

Evil Mannequins is a Horror Survival game built in Unity Engine. It won 1st place at the Gameathon at V.K. Krishna Menon College in 2026. The player must survive against mannequins that come to life in a terrifying environment.

Mechanics & Systems
  • Horror survival loop — player evades AI-driven mannequin enemies.
  • Custom enemy AI in C# using Unity NavMesh for detection and chasing.
  • Atmospheric lighting and shadow system to build tension and fear.
  • Full game state management — menu, gameplay, game-over, win screens.
  • Responsive audio cues tied to enemy proximity and player actions.
What I Learned
  • End-to-end development — from concept to polished, competition-ready build.
  • Building AI with Unity NavMesh and C# state machines.
  • Designing horror mechanics that create genuine tension and fear.
  • Delivering a complete product under competition deadline pressure.
Why It Matters

This project proved I can design, build, and ship a complete game — and win a competition doing it.

UnityTroll Game3D
Exit Through Portal: The Troll Game
Summary

Exit Through Portal: The Troll Game is a first-person mobile troll game built in Unity Engine. The player spawns in a random area and must find the one true exit among a field of decoy portals. Reaching each portal requires clearing a short parkour-style challenge — but picking the wrong one triggers a scripted troll event: jumpscares, meme references, fake UI overlays, and other unexpected twists. Every troll event ends the moment the skip button appears a few seconds in, and finding the correct portal wins the game.

Mechanics & Systems
  • Built with Unity 3D (URP), C#, the New Input System, and Android SDK, targeting first-person mobile play with 13+ unique portal mechanics — jumpscares, fake UI overlays, dynamic screen manipulation, and meme-driven twists.
  • Used Unity NavMesh and NavMeshAgent for AI chase sequences, baking separate NavMesh surfaces per scene so enemies could path around the parkour geometry without runtime recalculation cost.
  • Designed a modular portal system using a base Portal script with swappable trigger components (teleport, notification, troll event), so new portal types could be added by composing components rather than writing new logic each time.
  • Structured scene hierarchies with deliberate object parenting — grouping pooled UI elements, particle effects, and portal triggers under dedicated empty transforms — to keep the hierarchy manageable and make batch enabling/disabling of troll sequences cheap.
  • Hit a stable 30+ FPS on low-end Android devices by baking static lighting instead of using real-time GI, pooling dynamic UI objects instead of instantiating/destroying them on every troll trigger, reducing shadow resolution/distance, and capping particle system counts per effect.
  • Built a multi-scene architecture with a cinematic main menu — smooth camera transitions, looping music, and a black-screen fade system for seamless loading between menus and gameplay.
What I Learned
  • How to bake and use NavMesh surfaces per-scene for AI pathing, and how to keep agents from taking shortcuts through parkour geometry that wasn't meant to be walked on.
  • Designing a modular, component-based portal system — this was my first time building trigger logic as swappable components instead of one big script per object, which made adding new portal types dramatically faster.
  • Practical object pooling for dynamic UI — instead of instantiating/destroying troll UI elements every trigger, reusing a pool cut GC spikes and smoothed out frame drops on low-end devices.
  • How much deliberate parenting/hierarchy structure matters for performance and sanity — grouping objects logically made batch enable/disable operations (like ending a troll event) much cheaper and easier to debug.
  • Real mobile optimization trade-offs for the first time — baked lighting vs. real-time GI, shadow resolution vs. draw calls, and how to profile on an actual low-end Android device rather than just the Unity Editor to find where FPS was actually being lost.
  • Using the New Input System for the first time, and structuring input so it could be swapped or extended without touching gameplay code.
Why It Matters

This project pushed me to design original, self-contained gameplay systems from scratch rather than following a tutorial — and to build something that's genuinely fun to watch other people play.
